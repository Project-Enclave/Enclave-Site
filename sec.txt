    fix: sender can now re-read their own E2E messages

    decrypt() was always doing local_priv × sender_pub. When the local
    node IS the sender, sender_pub == local_pub, giving a wrong shared
    secret and an AES-GCM auth failure.

    Fix: detect the self-send case (sender_pub bytes == local pub bytes)
    and, when true, fall back to local_priv × peer_pub_b64 (the recipient
    pub key, supplied by the caller). decrypt() gains an optional
    peer_x25519_pub_b64 kwarg; passing it is only required when the caller
    might be the original sender re-reading the message.

    fix: two real bugs blocking "multiple profiles, same device" discovery

    You asked me to verify the existing multi-profile support actually
    works for running simultaneously on one device. It mostly did -- ports
    are correctly auto-allocated per profile (core/profiles.py), no
    collisions, both processes run fine side by side. But LAN discovery

    independent, stacked reasons. Found both by testing actual concurrent
    processes rather than trusting that "the code looks right":

    1. discovery.py used UDP broadcast (255.255.255.255) with the listen
       socket bound via SO_REUSEPORT, intending to let multiple local
       profiles each receive announcements. On Linux, SO_REUSEPORT
       load-balances incoming datagrams across every socket sharing a port
       -- the kernel picks exactly ONE of them per packet, it does not
       deliver a copy to each. Confirmed this directly: two local Discovery
       instances, isolated from all other app code, showed "exactly one
       side sees the other" in 3 out of 3 trials, never both, never
       neither. Fixed by switching to UDP multicast (239.255.42.99), which
       verifiably fans a single sent packet out to every joined socket on
       the host -- checked that property with a standalone raw-socket test
       before touching any app code. Also added a second early announce
       ~2s after the first (still well before the steady-state 30s
       interval) to close a real, if minor, cold-start race: a node's
       first announce can be sent before a peer's own multicast group-join
       (IP_ADD_MEMBERSHIP) has completed, and multicast doesn't buffer
       packets for late joiners.

       logging.getLogger("network") -- a logger nothing in the codebase
       ever attached a handler to. It was invisible except for WARNING+

       stderr, which is exactly why discovery's warning-level messages

       (including "saw peer" -- the literal evidence of successful
       discovery) never appeared anywhere. This was a pure observability

    add core/network/dht.py — Kademlia-style DHT for internet discovery

    Same protocol family BitTorrent's mainline DHT (BEP 5) uses, adapted for
    this app: instead of "who's seeding this infohash," a node announces
    "I'm reachable at this address for this user_id," and a lookup asks the
    swarm "who has announced for this hash" instead of asking for torrent
    peers.

    Read core/network/dht.py's module docstring before enabling this --
    three things worth saying plainly here too:

    - It does not solve NAT traversal. It only helps find a peer's last-
      announced address; if that address isn't actually reachable (most
      home routers block unsolicited inbound traffic without port
      forwarding/UPnP), you'll find them but still can't connect. Same
      limitation real BitTorrent DHT has -- it's a lookup mechanism, not a
      hole-puncher.
    - There's no public bootstrap infrastructure. A fresh node can't join
      the DHT on its own -- you need at least one already-reachable peer's
      address to bootstrap from (a second device, a friend's node, a VPS
      you control), same as a torrent client needs a bootstrap node.
    - Opt-in, not opt-out (dht_enabled config setting / --dht flag).
      Joining a public DHT means announcing your address to a swarm of
      strangers -- a meaningfully different exposure than LAN broadcast.
      DHT lookup RESULTS get the exact same key-pinning treatment
      discovery.py already applies to LAN results before ever being
      trusted -- the DHT is a far more adversarial environment than your
      own LAN, so an already-known peer showing up with different keys via
      a DHT result gets rejected exactly like a spoofed LAN broadcast
      would.

    Implementation: 160-bit id space (SHA-1 of user_id), standard k-buckets
    (k=8, oldest-evicted-first replacement rather than full ping-and-replace
    -- correct behavior, less machinery, appropriate at this scale),
    iterative find_node (alpha=3), JSON-over-UDP RPC (ping/find_node/
    find_value/announce), TTL-based storage expiry with periodic republish.

    Integration: Node gets an optional DHTNode when dht_enabled. send() falls
    back to a DHT lookup when a peer isn't in the local peer_store, instead
    of just failing. New CLI flags on `main.py run`: --dht, --dht-bootstrap
    (repeatable), --dht-public-ip.

    Found and fixed three real bugs while building this, the same way as
    everywhere else this session -- by testing actual multi-node exchanges,
    not by reading the protocol description and assuming the code matches
    it:

    1. Messages never actually carried each node's own DHT id anywhere
       except in OTHER-nodes-discovered lists. The very first test (three
       real node instances, real sockets) showed nodes never learning each
       other directly despite valid exchanges happening -- fixed by having
       every query and reply carry the sender's own id, and having both
       sides of any successful RPC round-trip register each other properly
       instead of the broken placeholder I'd used originally (hashing the
       source ip:port string, which obviously isn't a node's real id).

    2. announce_self() never included the announcer's own IP in the
       announced value -- only the port. For LAN broadcast the source IP
       comes for free from the received packet, but a DHT value gets
       returned by a THIRD node, not the announcer -- so the ip has to be
       IN the stored value or there's no way to know where to actually
       connect. Fixed with a ping-echo address self-detection (same
       principle STUN uses: ask a peer what source address they saw you
       connecting from) plus an explicit override for when you already know
       your own reachable address (e.g. a VPS).

    3. announce_self() only pushed the value to the K closest OTHER nodes
       find_node() returns -- which structurally never includes yourself,
       since routing tables don't hold a contact for your own id. In a
       small network (confirmed with exactly the 2-node case), that value
       can end up stored only on a peer who then gets asked about a DIFFERENT
       key when someone looks YOU up -- the announcer never had a queryable
       copy of their own announcement. Fixed by also self-storing on
       announce, which real Kademlia implementations do too, for the same
       resilience reason.

    Also hit a real environment quirk while testing address self-detection:
    this sandbox's container networking rewrites loopback UDP source
    addresses to a synthetic 192.0.2.2, which isn't a real dialable address
    here -- confirmed with a raw-socket reproduction independent of any DHT
    code, so it's a property of this container, not the technique (which is
    standard, well-established practice on real networks). Documented as a
    known caveat; the explicit --dht-public-ip override exists partly for
    exactly this class of environment (also relevant for real users running
    under Docker/WSL/similar).
